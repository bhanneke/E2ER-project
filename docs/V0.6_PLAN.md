# v0.6 — Targeted-Revision Discipline

End-of-session plan — May 20, 2026. Design record only; no code yet.
Captures a drift problem discovered while documenting v0.5: the
revision phases rewrite the whole paper instead of patching the parts
reviewers flagged. v0.6 fixes that.

This is strictly a Lane A change set. Lane B (literature) and Lane C
(data) are untouched.

---

## The drift problem

`PipelineRunner.run()` (`src/core/strategist/runner.py:129-178`) walks
a 7-phase sequence. Six of the seven phases are well-scoped. **Only
the revision phases let a single specialist rewrite `paper_draft.tex`
from scratch**, and the iterative phase lets the strategist
re-dispatch `paper_drafter` (which also writes the whole file).

The polish phase already shows the right pattern: deterministic
selection of which specialists to run based on what evidence says is
broken (`_select_polish_specialists`, `runner.py:822-847`). v0.6
extends that discipline to the revision and iterative phases.

### Three concrete drift sources

| # | Where | What happens | Why it's wrong |
|---|---|---|---|
| 1 | `_run_revision_phase` MAJOR_REVISION branch (`runner.py:601-621`) | Single `revisor` work order with `focus="Revise paper based on review aggregation: {rationale}"`, outputs to `paper_draft.tex` | Revisor sees full draft + generic aggregator rationale, then writes the whole `.tex` from scratch. No instruction to preserve unchanged sections. No revisor-specific skill file exists (`grep -rn "revisor" skills/` returns zero hits — skills are the generic `writing/paper-structure`, `writing/personal-style`, `reasoning/anti-slop`). |
| 2 | `_run_self_attack_phase` critical-findings branch (`runner.py:417-436`) | Top-3 critical findings → **three parallel `revisor` work orders, all writing to `paper_draft.tex`** via `execute_parallel` | Three concurrent rewrites of the same file. Last-writer-wins on disk; the other two revisions are silently discarded. The surviving one was written without knowledge of the other two findings. |
| 3 | `_run_iterative_phase` (`runner.py:334-388`) | Strategist re-decides each iteration; can re-dispatch `paper_drafter` (whose `output_file=paper_draft.tex` per registry) on iteration 2, 3, ..., 6 | Every iteration potentially overwrites the entire draft. The ceiling check detects when iterations stop improving the paper, but doesn't detect when they re-introduce problems by rewriting things that were previously fine. |

### Symptom: v0.5's verify_numbers backstop

The anti-hallucination gate added in v0.5 catches drafters that invent
table numbers. It's a *symptom* of source #3 — paper_drafter is
allowed to write the full paper from scratch with no constraint
linking its numbers back to source artifacts. A scoped patch revisor
that only touches table cells flagged by `verify_numbers.mismatches`
would be less invasive than rejecting the whole paper at the gate.

v0.5's REJECTED + resume flow lets the operator manually re-run the
pipeline after revising source artifacts. v0.6 makes the in-pipeline
revisor capable of doing that mechanical fix itself, without operator
intervention.

## What's already correct (don't break in v0.6)

Two patterns in the current pipeline match the original intent. v0.6
should preserve and extend them, not replace them:

1. **Polish phase: evidence-driven selection.**
   `_select_polish_specialists` reads `self_attack_report.json`, maps
   each finding category → specialist
   (`equilibrium → polish_equilibria`, `numerics → polish_numerics`,
   etc.), and runs only the matching subset. `polish_formula` always
   runs as a safety net. This is the pattern v0.6 generalizes.
2. **Mechanical review aggregation.** The aggregator
   (`review_aggregator.py`) parses `OVERALL SCORE: N/10` from each
   reviewer file on disk and applies a deterministic 3-rule verdict
   (ACCEPT / MAJOR_REVISION / HARD_REJECT / MECHANISM_FAIL). No LLM
   judgment in the verdict path. v0.6 extends this by feeding the
   structured findings (not the prose rationale) into the revisor.

## The three changes

### 1. New specialist: `patch_revisor`

**Replaces** the generic `revisor` in both revision dispatch sites.
The existing `revisor` entry stays in the registry for one release
cycle as a deprecation shim — the runner stops dispatching it but
removing the registry entry would break any test fixtures that
reference it.

**Contract:**
- Input: structured findings list. Each finding has a `target` field
  (one of: `section:<name>`, `table:<label>`, `paragraph:<id>`,
  `references`, `abstract`) and a `problem` field (the specific issue
  to fix).
- Output: edits scoped to the targets. Implementation choice: either
  unified diff against `paper_draft.tex`, or section-scoped writes to
  `paper_draft.tex.patch` that a deterministic merger applies. The
  diff approach is cheaper to implement; the patch-file approach is
  easier to debug. Decide during scaffolding.
- Pre-loaded context: only the sections/tables named in `target` from
  the current draft, plus the findings being addressed. **Not** the
  full draft.

**New skill file:** `skills/files/writing/scoped-revision.md`. Single
load-bearing rule: "Edit only what's named in the work order's
findings. Do not rewrite, restructure, or stylistically polish
anything that isn't explicitly targeted. If a finding requires
changes outside its target, return a structured 'expand-scope'
response instead of silently editing."

**Output file:** `paper_draft.tex` (after merge) — unchanged from
the operator's perspective; the dashboard still reads one file.

### 2. Findings collector — structured input to the revisor

The runner currently feeds the revisor the aggregator's prose
rationale, which lossy-compresses every reviewer's specific findings
into one paragraph. v0.6 introduces a `Finding` dataclass shared
across all three revision call sites:

```
@dataclass
class Finding:
    source: str          # "reviewer:technical" | "self_attack" | "verify_numbers"
    target: str          # "section:identification" | "table:T1" | ...
    severity: int        # 1-10
    problem: str         # one-sentence specific description
    suggested_fix: str   # one-sentence concrete suggestion
```

Three collectors emit `Finding` lists:
- `_collect_review_findings(scores)` — parses structured findings from
  each `review_*.md` file (requires extending the reviewer prompt's
  closing format with a `FINDINGS:` JSON block).
- `_collect_self_attack_findings(report)` — already structured;
  existing `SelfAttackFinding` maps directly.
- `_collect_verify_numbers_findings(report)` — wraps
  `Mismatch` objects with `target="table:..."` and `source="verify_numbers"`.

The collectors run before any revisor dispatch. The revisor's work
order carries a JSON-serialized list of `Finding` objects in `focus`.

### 3. Bounded iterative phase

The strategist's system prompt (`engine.py:27-103`) gets a hard rule:
**after iteration 1, dispatching `paper_drafter` is forbidden**.
Iterations 2+ may dispatch only:
- `section_writer` with a `section:<name>` in `focus`
- design specialists (`identification_strategist`, `econometrics_specialist`, etc.) for upstream changes
- `patch_revisor` for surgical fixes

This is enforced two ways:
- Soft: instruction in the strategist's system prompt + an example for
  iteration 2.
- Hard: runner-side check in `_run_iterative_phase` that drops
  `paper_drafter` work orders on iterations ≥2 and logs a warning. The
  strategist eventually learns from the warning in logs (when we
  retrain prompts), but the hard check protects us in the meantime.

The self-attack revision (drift source #2) gets **serialized**, not
parallelized. Top-3 findings → one `patch_revisor` call with all
three in its findings list, not three parallel calls. Cheaper, no
write race, and the model sees all three problems together so it can
notice interactions between them.

## How the three sources resolve

| Drift source | Fix |
|---|---|
| #1: MAJOR_REVISION dispatches one full-rewrite revisor | `_run_revision_phase` collects findings from review files + verify_numbers report, dispatches `patch_revisor` with the structured findings list |
| #2: Self-attack runs three parallel revisors on the same file | `_run_self_attack_phase` builds one findings list from top-3 critical findings, dispatches **one** `patch_revisor` call |
| #3: Iterative phase lets strategist re-dispatch `paper_drafter` | Runner-side guard in `_run_iterative_phase` rejects `paper_drafter` on iter≥2; strategist prompt updated to dispatch `section_writer` instead |

The patch_revisor specialist is the same in all three call sites —
the only thing that varies is which collector populated the findings.

## Verify_numbers becomes proactive, not just defensive

In v0.5, `verify_numbers` is a pre-review gate: critical mismatches →
REJECTED, operator restarts. In v0.6 it can also feed the
`patch_revisor`. New behaviour:

1. `verify_numbers` runs as before.
2. If `critical_mismatches` is non-empty AND we haven't yet exhausted
   one v0.6-introduced "auto-patch" budget (default: 1 attempt), the
   collector wraps each mismatch as a `Finding` with
   `target="table:..."` and dispatches `patch_revisor` instead of
   transitioning to REJECTED.
3. `verify_numbers` runs again after the patch. If it still has
   critical mismatches, **then** transition to REJECTED — the model
   couldn't fix it; operator decides.

This is the original-intent loop the v0.5 design left out: detect →
patch → re-detect. v0.5 did detect → reject; v0.6 closes the loop.

## What v0.6 doesn't do

Out of scope, kept for v0.7 or later:

- **Section-level dependency tracking.** A change in the
  identification strategy implies changes in the methods section and
  possibly the empirical section. v0.6's `patch_revisor` patches what
  the findings name; it doesn't propagate. A future change could add
  a per-section dependency graph and re-emit findings on dependent
  sections.
- **Replacing `paper_drafter` entirely.** v0.6 forbids re-dispatch on
  iter≥2 but keeps it for the initial draft. A future version could
  build the draft section-by-section via `section_writer` from the
  start, removing the full-rewrite tool entirely.
- **Reviewer prompt schema change.** Extending the reviewer closing
  format to emit `FINDINGS:` JSON is part of v0.6, but the broader
  structured-output discipline (typed reviewer responses end-to-end)
  is a separate effort.
- **Re-review of patched sections.** v0.6 patches and re-renders; it
  does not re-invoke reviewers on patched sections. That would
  require per-section review state, which the current
  `review_*.md`-per-reviewer layout doesn't support.

## Implementation order

1. **Findings dataclass + collectors** (~1 day) — pure refactor of
   how revision inputs are assembled. No behaviour change yet.
2. **`patch_revisor` specialist** (~1 day) — new skill file, new
   registry entry, dispatcher wiring. Output is still
   `paper_draft.tex`. Decide patch-vs-diff format here.
3. **Wire MAJOR_REVISION through patch_revisor** (~0.5 day) — replace
   the single-revisor dispatch in `_run_revision_phase`.
4. **Wire self-attack through patch_revisor** (~0.5 day) — serialize
   the parallel calls, batch findings.
5. **Wire verify_numbers loop** (~0.5 day) — auto-patch budget,
   re-run after patch.
6. **Iterative-phase guard** (~0.5 day) — runner-side rejection of
   `paper_drafter` on iter≥2, strategist prompt update.
7. **Tests** (~1 day) — regression test per drift source:
   - `test_patch_revisor_does_not_rewrite_unchanged_sections`
   - `test_self_attack_dispatches_one_revisor_not_three`
   - `test_iterative_phase_rejects_paper_drafter_after_iter1`
   - `test_verify_numbers_auto_patch_loop_then_reject`
   - Updated end-to-end fixture covering all three call sites.
8. **Live-run validation** (~1 day) — re-run the v0.4.5 motivating
   papers + one new fresh paper. Cost should drop materially because
   parallel-revisor waste is gone.

Total: ~6 dev-days plus 1 live-validation day. All Lane A.

## Architecture invariants v0.6 adds

To carry forward into the invariants section of `docs/NEXT_STEPS.md`:

1. **`paper_drafter` runs at most once per paper.** Pinned by a runner
   test that asserts iteration ≥2 dispatches drop `paper_drafter`
   work orders.
2. **Revisions are dispatched serially, never in parallel, against
   `paper_draft.tex`.** Pinned by a test that intercepts a self-attack
   with three critical findings and asserts exactly one
   `patch_revisor` work order is created.
3. **The revisor receives structured `Finding` objects, never a
   free-text aggregator rationale.** Pinned by a test that constructs
   review files with `FINDINGS:` blocks and asserts the resulting
   work order's `focus` parses as JSON.
4. **`verify_numbers` runs twice on a paper with auto-patchable
   mismatches.** Pinned by a test that simulates a fixable mismatch
   and asserts the second `verify_and_save` call finds zero criticals.

## Why ship v0.5 first, not roll v0.6 into it

v0.5 is bookkeeping: distinguishing REJECTED from FAILED, plumbing
methodology, catching hallucinated numbers. It does not change the
revision *shape*. v0.6 changes the revision shape — new specialist,
new contract, new findings dataclass. Mixing them would make either
release impossible to validate against the v0.4.5 motivating runs.

Ship v0.5 → confirm it on the three motivating papers → tag v0.5.0 →
branch v0.6 from there.
