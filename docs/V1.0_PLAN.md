# v1.0 plan — from "catches its own failures" to "produces papers"

> **Status**: proposal (2026-08-20). Extends [`V0.9_PLAN.md`](V0.9_PLAN.md)
> and honours the calibration in [`VERSIONING_RESET.md`](VERSIONING_RESET.md).
> Written after three live canary runs of the validation cell on 2026-08-20,
> which are the first real exercise of the six robustness-review fixes.

## The three gates, restated

We are at **0.8.2**. "Moving to v1.0" is not one milestone, it is three, and
conflating them is what produced the v0.9 overreach the versioning reset
corrected.

| Gate | Definition (from `VERSIONING_RESET.md`) | State |
|---|---|---|
| **v0.9.0** | One paper survives review under real conditions (M5) | ❌ never achieved |
| **v1.0 candidacy** | Repeat success across methodologies | ❌ blocked on v0.9.0 |
| **v1.0** | The API is stable enough to promise | ❌ not costed |

The load-bearing fact: **the pipeline has still never produced a completed
paper.** Three canaries on 2026-08-20 died three different ways. Every one of
those deaths was a *reliability* defect — the pipeline failing to run — and
not once a *research-quality* defect. That is the whole near-term roadmap.

## What the three canaries actually proved

Worth stating plainly, because it is better news than the failure count
suggests. The robustness review's fixes were "implemented but never exercised
by a live run". They have now been exercised, and they work:

- **Canary #1** wrote `econometric_spec.md` before `run_estimation.py` — the
  write-order fix holds. All 8 specialists returned success. Reached a 90 KB
  compiled PDF.
- **Canary #2** died at `data_architect`, and *the contract check caught it
  correctly under regime `off`*: `contract violation — data_dictionary.json:
  file not written`. Recommendation #2 — reliability blocks in every regime —
  is real and firing.
- **Canary #3** reached rendering, and the repair loop cut 12 unresolved table
  references to 4 in its one permitted pass.

So the gates work. What does not yet work is the machinery that is supposed to
*recover* from a gate firing.

## Phase 1 — make a run finish  → unblocks v0.9.0 / M5

### 1.1 Retry a failed parallel batch (the canary #2 death)

`execute_parallel` (`src/core/specialists/dispatcher.py:126`) calls
`execute_work_order` exactly once per work order. There is no retry. When the
batch is size 1 — which it always is at `MAX_CONCURRENT_SPECIALISTS=1` — "1/1
specialists failed" is also "every specialist failed", and the pipeline dies
on the spot:

```
13:03:56 | data_architect: tool_loop returned (success=True, tools_called=0)
13:03:56 | data_architect: contract violation — data_dictionary.json: file not written
13:03:56 | execute_parallel: 1/1 specialists failed
13:03:56 | Pipeline failed
```

Three seconds from a single flaky turn to a dead 30-minute run.

The irony is that every piece of the recovery already exists and is
unreachable from here. `_MAX_SPECIALIST_ATTEMPTS = 3` lives in the runner's
*sequential* path only. `read_contract_feedback` is built to inject the
violation into the next attempt's prompt — coached retry, exactly what
recommendation #2 says regime `off` must keep — and on the parallel path there
is never a next attempt to inject it into.

**Fix**: retry within `execute_parallel`, bounded by `_MAX_SPECIALIST_ATTEMPTS`,
so the coaching machinery gets its second attempt. Contained, ~30 lines, and it
converts the single most expensive failure mode into a recoverable one.

### 1.2 Prove `ddbb4ff` and 1.1 on a fresh canary

Fresh process on a fresh port — the API server runs without `--reload`, so a
running server executes the code it imported at boot. This has already cost us
one misleading measurement; it must not cost another.

### 1.3 Iterate

Budget two to three more canaries. Each one that dies differently is
information, not waste — that has been the pattern all week.

**Exit criterion**: one empirical paper completes end-to-end and passes its own
gates. That is M5, and that is `v0.9.0`.

## Phase 2 — make a run *measurable*  → the OrgSci critical path

Phase 1 gets a run to finish. Phase 2 makes finishing mean something. This
phase, not Phase 3, is what the submission depends on.

### 2.1 `repeats: 3` in the cell config

`experiments/validation_cell.yaml` sets `repeats: 1`. Three identical runs on
identical code failed three different ways, so at n=1 the experiment cannot
distinguish a design flaw from an unlucky draw. A referee will ask how many
times it was run, and the honest answer must not be "once".

### 2.2 Stamp run identity into the run record

Git SHA, interpreter path, backend, model, concurrency. Without it there is no
way to prove after the fact which code produced which result — and the
stale-server hazard means that is a live risk, not a theoretical one.

### 2.3 Then the 3×3 matrix

Only once 2.1 and 2.2 hold. Running it earlier produces numbers nobody can
defend.

**Exit criterion**: the matrix's variance is attributable — to the regime, to
the backend, or to the draw, and you can say which.

## Phase 3 — repeat success across methodologies  → v1.0 candidacy

The honest inventory in `VERSIONING_RESET.md` still stands here, and none of
these are touched by Phases 1–2:

| Surface | Gap |
|---|---|
| End-to-end theoretical paper | never run live |
| `theory_specialist` | mocked only |
| `mixed` methodology | no starter, never run |
| Reviewer scoring + aggregation | never pressure-tested; every test pins `Score: 7/10`, so we do not know how aggregation handles a genuinely split panel |
| 133+ skill files | shipped, mostly unverified against real output |
| `examples/showcase/` | still empty of a real run |

The reviewer-panel gap deserves emphasis. A review system that has only ever
been tested against unanimous 7s is not a review system yet, and "the paper
survived review" is the v0.9 gate — so a fabricated consensus would make the
gate vacuous.

**Exit criterion**: ≥3 completed papers across ≥2 methodologies, at least one
of them theoretical.

## Phase 4 — what v1.0 actually promises

v1.0 in SemVer is a commitment not to break your callers. That is a different
kind of work from everything above, and it should not start until Phase 3
holds.

- **Open defects**: CLI error strings truncate at ~500 chars (why the pilot's
  eight subprocess failures were never explained); the false-positive
  econometrics gate; the unreachable `estimation_gate` (Finding 5.3); the
  `blocked_by`/`shadowed` split in gate event payloads (Finding 5.4).
- **Complexity** (robustness review rec #6): 57k lines across 256 files, where
  v1 ran in 27k across 82. Every guard added since has made the next failure
  harder to trace. v1.0 should ship a smaller surface than 0.8.2, not a larger
  one.
- **Release mechanics**: CHANGELOG cutover, README calibration, the
  standardised bump → PR → tag → PyPI flow.

---

## What we are explicitly not doing

New data providers, new literature providers, and the five `PORTING_PLAN.md`
features. Every canary death to date has been a reliability defect, and
features add exactly the surface that is failing. The issue forms remain the
front door; we build providers when a real user asks.

## The tension worth naming

The OrgSci submission and v1.0 share Phases 1 and 2 and then diverge. The paper
needs runs that are *measured*; v1.0 needs runs that *succeed across
methodologies*. Phase 3 is v1.0-only and should not block the submission — but
Phase 2 blocks both, and it is the phase most likely to be skipped under time
pressure, because it produces no new capability. Skipping it is how the
submission ends up resting on n=1.
