# Publishing a study

`e2er publish <folder>` describes an exported study, writes its dossier and, with `--to https://e2er.org`, publishes the description. The files stay on your computer or in your repository; e2er.org receives the description, the dossier and a fingerprint (SHA-256) of every file. With `--github` the files go to a public GitHub repository of yours (see below). The dossier's address (in the paper's footnote, e2er.json and the output) is on the platform you publish to: `--to`, else `E2ER_URL`, else https://e2er.org. Prepare with `--offline` under the same `E2ER_URL` you publish to, or the footnote changes when you publish.

## Publish asks first

Nothing leaves your computer before you say yes. When the rehearsal of the request has passed, `e2er publish` prints what goes where and asks:

```
What goes where:
  https://e2er.org (ada/road-deaths): the description, the dossier, file fingerprints
  GitHub github.com/ada/studies, folder road-deaths: the study's files as `e2er pack` ships them (public)
Publish 'Road deaths in 2021' to https://e2er.org as ada? Files to GitHub ada/studies/road-deaths. [y/N]:
```

Only `y` or `yes` publishes; anything else (or Enter) sends nothing, pushes nothing and leaves the folder as it was. With `--zenodo` the question names the Zenodo deposits too. A run without a terminal on standard input (a script, a CI job) cannot be asked, so it needs `--yes` (`-y`); without it publish refuses at once, with nothing sent. `--dry-run` never asks and never sends, with or without a terminal. The dashboard's Publish button asks the same question in the browser and sends the yes along with the request (`confirm: true` on `POST /api/papers/<id>/publish`); the local server refuses a publish without it.

Before the question, `--to` checks with the platform (`GET /api/v1/me`) that you are signed in, that `--owner` is one of your account's handles and, when the token is one for a single study (`e2er login --scope`), that it is this study's; otherwise nothing is sent, deposited or pushed.

**Held for your confirmation.** When one account publishes more than three versions of a study, or more than three new studies, within ten minutes, e2er.org keeps the extra ones back: it answers "held: confirm in your browser" (HTTP 202) and lists them on your account page, where you confirm or discard each, signed in in the browser. That is not an error: publish prints the address to confirm at, records the version in `.e2er/link.json` as held (`"held": true`, the hold's id and the address; no version number yet) and exits 0. `e2er status` says it is waiting. Zenodo deposits of a held version stay drafts (no DOI is minted) until you have confirmed it; run the same command again then. A later publish without the run's database carries over the held version's dossier only once it is confirmed.

## Publishing from CI: a token for one study

Your personal login (`e2er login`, kept in the system keychain, or in `~/.e2er/credentials.json` with mode 0600 where there is none) can publish any study under your handles. A CI job should not hold it. Give it a token that can only publish new versions of one study:

```
e2er login --scope study:ada/road-deaths | gh secret set E2ER_TOKEN      # approve in the browser
e2er token create --study ada/road-deaths | gh secret set E2ER_TOKEN     # or with your personal login, no browser
```

The token is printed once, alone on standard output, so it can go straight into the CI secret; e2er does not keep it, and your personal login stays as it is. Such a token publishes new versions of `ada/road-deaths` only: it cannot create a study or a handle, cannot publish another study, cannot withdraw a study, and cannot create or list tokens. The study must already be published. In the CI job:

```
env:
  E2ER_TOKEN: ${{ secrets.E2ER_TOKEN }}
run: e2er publish ./study --owner ada --project road-deaths --to https://e2er.org --yes
```

`e2er whoami` with such a token says which study it is for. Revoke it on your account page (e2er.org/account) or with `e2er logout` run with it in `E2ER_TOKEN`, which ends that token and leaves a login saved on the computer as it is. On the platform the token is a row of `api_token` with the study in its `study` column (`POST /api/v1/tokens` with `{"study": "<owner>/<slug>"}`); e2er refuses to keep a token from a platform that does not limit it to the study.

## Running e2er inside your own test suite

When e2er runs inside a test runner it never uses your own login and never publishes anywhere but a local test server. A test run is one with `PYTEST_CURRENT_TEST` set (pytest sets it for every test, and a command a test starts inherits it), `E2ER_TEST=1` (set it for any other runner, or for a shell script of tests), or `CI=true` together with a test command (pytest, unittest, nose2, tox, nox). In a test run:

- e2er never reads or writes the system keychain or `~/.e2er/credentials.json`; the Zenodo token saved in Setup, by `e2er zenodo login` or in the keychain is not read either. Only `E2ER_TOKEN`, `ZENODO_TOKEN` and a credentials file the test names itself (`E2ER_CREDENTIALS`) are used.
- Every request to a platform or to Zenodo is refused before it is made unless it goes to `localhost`, `127.0.0.1` (or another loopback address), or the one address in `E2ER_TEST_SERVER`, for a local copy of the platform your tests run. `E2ER_TEST_SERVER` may never name e2er.org or one of its subdomains. The refusal says "e2er is running under a test runner … Nothing was sent."
- `gh` is not run and nothing is pushed to GitHub (e2er's own tests run a fake `gh` and say so with `E2ER_TEST_GITHUB=fake`).

So a test that calls `e2er publish --to https://e2er.org --yes` on a machine signed in to e2er.org publishes nothing. (On 2026-10-20 a run of e2er's own tests did, with the machine's keychain token; the guard is in `src/core/test_guard.py`.)

## The run's database

The dossier lists the steps of the run: each specialist with its model, each check, each of your actions as researcher, and the run's outcome. `e2er publish` reads them from the study's run database, which it finds the way the server does: `--db` when you give it, else the database the study folder's `.env` names (`DATABASE_URL`), else e2er's default `~/.e2er/papers.db`. The database must hold the run of the paper the folder was exported from (its id is in `provenance.json`); a database of another study is refused, and without one publish stops and says where it looked.

A folder published before whose database is gone (`.e2er/link.json` names the version it published) carries over that version's dossier instead. Publish fetches the dossier from the platform the folder was published to and uses it only when everything agrees: `.e2er/link.json` and `e2er.json` name it, the platform's latest version of the study is that dossier and that content, the document hashes to its id, and the data fingerprints are this folder's. The new version's dossier is that document with its steps, segments, events, components and outcome unchanged, the new availability (for instance the files on GitHub), and an amendment on `e2er.json` (`kind: "carried_over"`, `from_version`, `from_dossier`, the e2er version that published it) whose reason reads "published again with files on GitHub; run database not available, dossier carried over from version N". e2er.json's description of the run (agents, process, skills) is the earlier version's. No step is added, removed or rebuilt, and the output says what was carried over. A version published from somewhere else, another project, a dossier that does not hash to its id or an unreachable platform is refused, and nothing in the folder changes.

`--no-db` publishes a folder whose database is gone. The dossier then records the template, components and data but no steps, no commit and no researcher actions, says so (`run.workflow_recorded: false`), and the paper's footnote says so too.

Each part of a run that a process ran (every start and resume) is a segment with the e2er commit and version it ran on (`e2er.segments`); every step names its segment, and every template, specialist, skill and connector is pinned at each commit it ran on. A file git cannot find at that commit is recorded as unresolved. A skill is named by where it comes from: e2er's own as `skill:e2er/<category>/<name>`, a skill from an installed pack (`~/.e2er/skills/<pack>/<skill>.md`) as `skill:<pack>/<skill>`, the id e2er.org lists it under, so the dossier links the listed part and its author is credited. A pack's skill is not part of e2er and has no pin at an e2er commit. In runs started after e2er 0.12.1 the runner records, with each step, the SHA-256 of every file the step wrote and the skills it read; for runs before that, the dossier gives the exported file's hash, as `sha256_at_export`, to the last step that wrote it.

## What publish changes in the folder

Publish first checks that every file is still the one `provenance.json` lists; a folder edited after export is refused, and nothing in it changes. Publish then changes a few files: it points `paper.tex` at the bibliography the folder ships, escapes `refs.bib`, puts the demonstration disclaimer into (or takes it out of) the reproduction report, and stamps the paper's first page with the dossier link and, for a demonstration study, the disclaimer (the author line `<name> with e2er` only with `--name`). Each change is recorded in `provenance.json` as an amendment: the file, its fingerprint before (the exported one for the first change), after, and why. `e2er verify` checks that the amendments of each file link up.

## Data and code: public or private

You state separately whether the study's data and its code are public:

```
e2er publish ./my-study --owner you --project my-study --data private --code public \
  --repo https://github.com/you/my-study --commit 3b91f0e
```

Both are private unless you say otherwise; run in a terminal without the two flags, `e2er publish` asks. For private material, only fingerprints are published, never contents or an address. For public material, give its address with `--data-url` or `--code-url`; public code defaults to your repository. The dossier names the repository, not the commit: the dossier's address is in the paper's footnote and the paper's fingerprint in provenance.json, so a commit-dependent dossier would change the very files the commit holds. The commit (`--commit`) is recorded beside the files, in e2er.json and in the publish request; e2er.org stores it with the study version, reads every file at it and compares it with provenance.json and the published fingerprints. So you can prepare the folder (`e2er publish --offline`), commit it, and publish with `--commit`: nothing the commit holds changes.

The study page and the dossier show what you chose, for instance "data private · code public". A dossier lists availability only when something is public, so a private study's dossier address does not change.

### The paper

The paper is private unless you publish its PDF's address: `--paper public --paper-url https://…/paper.pdf`. Without `--paper-url`, a public paper points at `paper/paper.pdf` in your repository at `--commit`. The address goes into `e2er.json` and the publish request only, never into the dossier, so stating it changes no fingerprint: publishing the same folder again with `--paper public` keeps the version and adds the link.

### What readers see for what is not public

On e2er.org, a paper, data or code that is not public has a button "Ask the authors for …" on the study page and the dossier, with the number of readers who asked (no names). A signed-in reader writes a short message; e2er.org forwards it to the authors who have an account there, without showing anyone's address. The reader may agree to be answered by email. You find the requests on your page "My submissions" (e2er.org/me), with the command that publishes the item; publishing it on a new version closes every open request for it and tells the readers. You can also mark a request as answered privately, decline it, or stop receiving requests.

`e2er publish` and the dashboard's finish page say this in one sentence for each item you keep private, with the flag that publishes it. Data from a source with terms of its own get no such note: the note names the source and its reason, and readers on e2er.org see a link to the source instead of a request button. Each source states its own reason: Yahoo Finance's terms allow personal use only; the Global Macro Database's terms do not allow passing the data on outside the study's replication package; Gaia's terms allow non-commercial use only, with credit to ESA/Gaia/DPAC (CC BY-NC 3.0 IGO); the GISCO terms allow non-commercial use only, with the EuroGeographics notice on every map; WHO's terms allow use for public health purposes only, and no changes without WHO's written permission; GitHub grants no licence to redistribute the repository metadata. The README's data source table lists the same reasons, from the same definitions.

### Data with terms of use: the Global Macro Database

Data loaded with `e2er-data gmd` come under the GMD's terms (version 1.1, https://www.globalmacrodata.com/license.html): free for academic use; a study's replication package may include the GMD data it used, labelled as GMD data; the data may not be republished anywhere else. Whatever you choose, the study's description (`e2er.json`) names the GMD, its terms and its citation on the data files that hold GMD data, and the dossier lists each GMD load with the same. The GMD citation is added to the paper's references when the data are loaded.

Publishing the GMD data with the study (`--data public`, also with `--zenodo`) needs your confirmation. In a terminal, publish shows the terms and asks; otherwise add `--accept-data-terms gmd`. Without it, publish refuses and changes nothing. With `--data private` no confirmation is needed. A Zenodo deposit of GMD data takes Zenodo's licence "Other (Non-Commercial)" and states the GMD terms and citation in its description.

### Data with terms of use: Yahoo Finance

Data loaded with `e2er-data yfinance` come under Yahoo's terms of use (https://legal.yahoo.com/us/en/yahoo/terms/otos/index.html). The yfinance project notes that Yahoo's finance data are intended for personal use only; yfinance is not affiliated with Yahoo. The study's description names Yahoo Finance and these terms on the data files that hold Yahoo data. Yahoo publishes no citation format, so publish asks for no BibTeX entry; the dossier lists each load with the citation e2er wrote for it.

If the data stay private, readers on e2er.org see a link to Yahoo Finance instead of a request button, and publish does not suggest publishing them. Publishing them with the study (`--data public`) needs your confirmation that you know Yahoo's terms allow personal use only: in a terminal publish asks "Publish the Yahoo Finance data with the study although Yahoo's terms allow personal use only?"; otherwise add `--accept-data-terms yfinance`. e2er does not deposit Yahoo data on Zenodo: a deposit republishes the data for anyone to reuse, which no Zenodo licence reconciles with personal use only. `--zenodo` with public Yahoo data is refused before anything is written or sent; keep the data private to deposit the code alone.

### Data with terms of use: GitHub

GitHub's Acceptable Use Policies (section 7, Information Usage Restrictions) allow research use of public, non-personal information only if the resulting publications are open access. A study that used data loaded with `e2er-data github` is therefore published with its paper public: `e2er publish` refuses `--paper private` (the default) for it, says why, and changes nothing; add `--paper public --paper-url <address of the PDF>`, or set the paper to public on the finish page, which states the same reason next to the paper. GitHub also grants no licence to redistribute the repository metadata, so publishing the data with the study needs `--accept-data-terms github`, and the replication package loads them again.

## A DOI for public data and code in one step

`--zenodo` deposits the public data and code on Zenodo with your own account and records the DOIs:

```
e2er zenodo login       # once: paste a personal token from zenodo.org
e2er publish ./my-study … --data public --code public --zenodo
```

`e2er zenodo login` opens Zenodo's page for a new personal token (`https://zenodo.org/account/settings/applications/tokens/new/`). Zenodo's form cannot be filled in from the address, so tick the two scopes yourself: `deposit:write` (upload) and `deposit:actions` (publish); any name will do, e.g. "e2er on <your computer>". Paste the token at the prompt; it is not shown, and e2er never prints or logs it (`pbpaste | e2er zenodo login` works too). e2er checks it with a request that changes nothing (`GET /api/deposit/depositions?size=1`) and stores it in the system keychain (service `zenodo.org`, username `token`), or, when there is no keychain (`keyring` is installed with e2er, but a headless Linux server or a CI runner has no backend for it, or the keychain refuses, e.g. without a GUI session), in `~/.e2er/credentials.json` with mode 0600. A token Zenodo refuses is not stored. Zenodo does not tell which scopes a token has, and testing `deposit:write` or `deposit:actions` would create or publish a record, so they are not tested: if one is missing, Zenodo refuses the first deposit (403), nothing is published, and an unpublished draft may be left in your Zenodo uploads. `e2er zenodo status` says whether a token is stored and whether Zenodo accepts it, without showing it; `e2er zenodo logout` removes it from this computer (delete it on Zenodo too, under Applications, to revoke it). `--sandbox` does the same for sandbox.zenodo.org.

In CI, or to override the stored token for one shell, set `ZENODO_TOKEN` (`ZENODO_SANDBOX_TOKEN` for the sandbox); the environment comes first, then the token saved in Setup, then the keychain, then the credentials file.

The data files are deposited one by one (as one zip `<project>-data.zip` when there are more than the 100 files a Zenodo record takes, or two files whose flattened names collide), the code (`code/` and `replication/`) as one zip. Each deposit names the study's authors with their ORCID iDs, its licence, and links back to the study page and the dossier; the DOIs go into the dossier and the study page. The files go from your computer straight to Zenodo; the token is never sent to e2er.org. Private material is never deposited.

A DOI, once minted, stays, so publish mints them last. With `--to`, before Zenodo is asked anything, publish checks that you are signed in to the platform, that `--owner` is one of your account's handles and, for a token for one study, that it is this study's token. The DOIs are then reserved (drafts, no DOI minted yet), everything that can still fail runs next (the dossier, the paper's stamp and recompile, the checks), the platform registers the study, and only after it took the request are the deposits published. Without `--to` (a deposit only) they are published before `e2er.json` is written. The reserved deposits are recorded in `.e2er/zenodo.json`; if publish stops on the way, or the platform refuses the request, the next publish reuses them, so a retry makes no new deposits and gives the same dossier. A draft you deleted on Zenodo's website is noticed (Zenodo answers 404), dropped from the record and reserved again; a new version's draft starts again from the published version.

A new version of the study (publishing the folder again) keeps a deposit's DOI when its files are the ones deposited (their MD5 checksums, recorded in `.e2er/zenodo.json` and, for deposits made before e2er recorded them, read from Zenodo). When they changed, publish makes a new version of the same Zenodo record (`newversion`): a new DOI under the record's concept DOI, holding exactly the new files; the dossier and the study page name the new DOI, and `.e2er/zenodo.json` keeps the earlier ones (`earlier`). A rehearsal (`--dry-run`) says which deposits would get a new version.

To try it first, use Zenodo's sandbox (`--zenodo-sandbox`, which implies `--zenodo`; token from `e2er zenodo login --sandbox` or `ZENODO_SANDBOX_TOKEN`, from sandbox.zenodo.org, a separate account with its own tokens; its DOIs start with `10.5072/` and resolve nowhere, so the study links the sandbox's record; the sandbox reserves a draft's DOI as `10.5281/zenodo.N`, production's prefix, and publishes it as `10.5072/zenodo.N`, which is the DOI publish records), or add `--dry-run` to see what would be deposited without depositing anything. Sandbox and real deposits are kept apart: `.e2er/zenodo.json` keeps the record of each host on its own (`hosts`: `zenodo.org`, `sandbox.zenodo.org`), so a rehearsal on the sandbox leaves the production deposits' record as it was, and a folder deposited only on the sandbox starts afresh on zenodo.org. A record written before e2er kept them apart is read as its one host's.

## The files in a public GitHub repository

`--github` puts the study's files in a public GitHub repository with your own GitHub login and links them from the study page and the dossier:

```
gh auth login                       # once; or set GH_TOKEN to a token of your own
e2er publish ./my-study --owner you --project my-study --github --to https://e2er.org
e2er publish ./my-study --owner you --project my-study --github you/studies --github-path my-study --to https://e2er.org
```

`--github` alone uses the repository `<your login>/<project>` and makes it (public) when it does not exist. `--github owner/name` uses that repository, making it when it does not exist; `--github-path <folder>` puts the study in a folder of it, so several studies can share one repository. The push uses the GitHub command line tool (`gh`) with your login, or `GH_TOKEN`; without `gh`, or when it is not logged in, publish says what to run and changes nothing. e2er.org never receives a GitHub token: it reads the public files at the commit, as for any study that names a repository. A private or archived repository is refused. There is no Zenodo deposit and no DOI on this path; the dossier id identifies the study, so `--github` does not go with `--zenodo`, `--repo`, `--commit`, `--path`, the `--…-url` options or `--data/--code/--paper private`.

**What goes up** is what `e2er pack` ships: the paper (PDF and LaTeX), the code, the results, the design and reviews, `reproduce.json`, `provenance.json`, `e2er.json` with the dossier, the package's `e2er-package.json` and its pinned environment, and the data whose source's terms allow passing them on. Data a source's terms keep out (the GMD, Yahoo Finance, the WHO GHO, Gaia, GISCO, GitHub) stay out, and so do files the study built from them: data files, and results that hold the source's rows (a units table of 244 regions, a figure spec with a point per star). A table of estimates or a handful of group means built from them is an aggregate and goes up (few rows against the source, no identifier of the source; the rule is in `docs/STRUCTURED_EXPORT_SPEC.md`), and so do the rendered figures. `e2er-package.json` names each left-out file with the reason, and `e2er reproduce` on a clone loads the data from the source again and builds the derived files with the study's own scripts; `e2er verify` on a clone skips a check that needs a left-out file and says which. Right before the commit, publish checks once more that no such file is in the folder, and it refuses a file that holds a key or token. `--dry-run` lists every file that would go up and every file that stays out, and pushes nothing.

**No key or token leaves the computer.** One check runs before files go out: `e2er pack`, the GitHub push and the Zenodo deposit refuse a file that holds a key or token (Anthropic, OpenAI, OpenRouter, GitHub `ghp_`/`gho_`/`ghs_`/`ghu_`/`github_pat_`, Google `AIza…`, AWS, e2er.org, a bearer header, FRED's `api_key=` or Zenodo's `access_token=` in a URL, or a long random value given to a name such as `ZENODO_TOKEN` or `fred_api_key`), whatever the file's size or encoding, and name the file. The export removes such values from the copies of the scratch logs and scripts in `code/scratch/` and says so in the README's notes. Take them out of a frozen file with `e2er redact <folder> --text <text>`.

**Files larger than GitHub takes (100 MB).** A data file over the limit (under `data/`, or a data output under `results/`, `misc/` or `paper/`) stays out when a step of the study's `reproduce.json` loads or builds it again. `e2er-package.json` declares it like a file left out under a source's terms, with `kind: "size"` (and `host`, `bytes`), and README.md says why and how a rerun gets it back: "`data/data.db`: too large for GitHub (145 MB); `e2er reproduce` loads the tables … again from the sources with code/get_data.py". A database counts as rebuilt only when every table a step reads is loaded again or built by a recorded step; a table no step reads (reproduce.json's `database`, `read: false`) is not needed and the README names it ("does not need the tables …"). A file over the limit that nothing gets back (no step loads or builds it, it holds a table no step builds, it is the published result itself, or it is not data) stops the publish, in `--dry-run` too, and nothing is pushed: "GitHub does not take files larger than 100 MB, and no recorded step of the study gets these back, so a copy without them could not be run again: data/data.db (145 MB): no step of reproduce.json loads it or builds it again". In a clone, `e2er verify` counts such a file as left out, not missing, only when the folder's `provenance.json` records it larger than GitHub's limit, and `e2er reproduce` loads and builds it again. `e2er pack` alone leaves nothing out for its size.

**README.md** opens with what a visitor of the repository needs: the title, the question, the dossier link, the demonstration label of a demonstration study, the e2er version, template and model, each data source with its terms and citation, the files left out and how `e2er reproduce` rebuilds them, and the licence of the code and text (`--license`, or a sentence that none was set). The export's own README follows below. The change is an amendment of README.md (`kind: "readme"`); like the paper's stamp, it names the dossier, so the dossier does not list it.

**How it is pushed.** One ordinary commit on top of the repository's default branch, never a force push; a repository that moved meanwhile is reported and nothing is overwritten. Only the study's folder changes: in the repository's root, or in `--github-path`. A folder that holds files of anyone else, or of another study, is refused, and so is a folder inside another study's folder. So is a study folder in which the repository tracks a symbolic link (a link committed by anyone with write access could point anywhere on your computer): every file is written only where it stays inside the clone. Publishing a new version adds a commit; publishing the same files again adds none.

**Only with a platform, and in this order.** The files go to GitHub only as part of a publish on a platform: `--to`, else the platform `.e2er/link.json` records (where the folder was published before), else e2er.org; publish says which. A run that would push without a platform is refused. The registration names the commit that holds the files, so the push comes first, and everything that can be checked before it is: the rehearsal of the request in a scratch copy, the sign-in on the platform (`GET /api/v1/me`; not signed in, or a refused sign-in, pushes nothing) and the files themselves. If the platform still refuses the registration after the push (an owner or dossier conflict it checks only when it receives the request), publish names the files' address and says so: run the same command again once the problem is solved; the files are already there, so no new commit is made, and the registration is sent again.

**What is recorded.** The repository, the folder and the commit go into `e2er.json` (`repository.url`, `path`, `commit`, with `host: "github"` and `left_out`), `.e2er/github.json` and the publish request. The study page shows "Files: github.com/<owner>/<repo>/tree/<commit>/<folder>"; the paper's address is `paper/paper.pdf` at the commit; public code and data link the `code/` and `data/` folders at the commit. The data are public only when at least one data file went up; otherwise they are private, and readers see the sources' links. The dossier names the repository and never the commit (see above), and the copy of `e2er.json` in the repository records neither the commit nor the paper's address nor the time of publishing: no commit can name itself. e2er.org checks every file at the commit against `provenance.json` and counts a data file the study declares as left out under its source's terms as left out, not missing.

## The study package next to the files

Every study published with `--github` or `--zenodo` also gets its study package: the `.e2er` file `e2er pack` writes (the same files, the same rules for what is left out; data a source's terms keep out are never in it), so a reader can inspect, verify and rerun the study on their own computer from one file. You keep it, next to the study's files; e2er.org records where it is, its size and SHA-256, and never stores the file.

- **With `--github`** the package the repository's folder was opened from becomes the file of a GitHub release of that repository, one release per study version: tag `<project>-v<N>`, file `<project>-v<N>.e2er`, at the pushed commit, made with your gh login. `N` is the number e2er.org gives the version (read from the study's public record before anything is pushed; the version that already has the same content keeps its number). A release that exists is used only when its tag names the pushed commit and its file has the same bytes; publish never moves a tag, never replaces a file and never marks the release as the repository's latest. If the upload fails, nothing is registered: run the same command again; no new commit is made. A repository connected to Zenodo's GitHub integration archives every release it publishes, so a study's release there becomes a Zenodo version too.
- **With `--zenodo`** the package is one more file in the code deposit (`<project>-v<N>.e2er`), and only with a public paper and public code (the package holds both; with private data it holds none, as `e2er pack --no-data`). The file does not count when publish decides whether the code changed; a code deposit published before and unchanged gets no new version, and the package goes with it only when it is the one that deposit already holds (otherwise publish says so and records none).
- **In double-blind mode** nothing is hosted: `e2er pack --blind` makes the file for the journal, as before.

The publish request and `e2er.json` record it as `package: {url, sha256, bytes, host, fingerprint}`; `fingerprint` is the package's own (its `e2er-package.json`, over its list of files). The copy of `e2er.json` inside the package names no package: no file can name its own hash. For the same reason the dossier document (which the package holds) cannot name it either: e2er.org keeps the record next to the dossier, on the study's versions and at `/api/v1/dossiers/<id>/package`, and shows "Download the study package (.e2er)" with its size and SHA-256 on the study page and the dossier page. `.e2er/package.json` keeps a local record of the release. `--dry-run` shows the package record the request would carry and the release it would make.

A reader gets and checks it with:

```
e2er fetch https://e2er.org/<owner>/<project>         # or a dossier's address; --version N for an earlier version
e2er inspect <project>-v<N>.e2er
e2er verify <project>-v<N>.e2er --against https://e2er.org/<owner>/<project>
e2er reproduce <project>-v<N>.e2er                    # the study's code, in a Docker container
```

`e2er fetch` reads the record with GET, downloads the file from where the authors keep it (https only, every redirect checked), checks its size and SHA-256 against the record, keeps nothing that does not match, and prints the three commands; it runs nothing. `e2er verify <file> --against` compares the package's fingerprint with the one recorded for that version (`package published`: the same fingerprint means the same files; the SHA-256 says whether it is the recorded file itself) and skips the comparison when no package is recorded.

## Taking personal data out before publishing

`e2er redact <folder> --text <text>` replaces every occurrence of the text in the folder's text files with `<redacted>` (`--replace` sets another word) and changes nothing else; before writing, it proves that the new file with the text put back is byte for byte the old one. Each changed file gets an amendment in `provenance.json`: `{path, kind: "redacted", sha256_before, sha256_after, reason: "personal contact details removed by the researcher", redaction: {replacement, count, offsets, removed_bytes, bytes_before, kept: {salt, hmac_sha256}}}`; `kept` is the HMAC-SHA256 of the bytes the redaction kept (the new file without the replacements), keyed with the random salt beside it (those bytes are in the published file anyway). The record never holds the text, nor a hash of it. A text longer than 256 bytes, or an empty replacement, is refused: contact details are short. `sha256_before` is keyed (`hmac-sha256:…`, with a salt kept on this computer in `~/.e2er/redaction-salt`): a plain fingerprint of the earlier file, with the offsets, lets anyone confirm a guess of a short text such as a phone number by trying. It stays a plain SHA-256 only where the earlier fingerprint is public anyway: a pre-registered plan file (its frozen fingerprint is in the lock file) and a folder published before (its fingerprints are on the platform). For a text shorter than 16 characters redact warns, and says whether such a public fingerprint exists. The next publish shows the redactions in the dossier. `e2er verify` checks each record against the file: the replacement sits at every recorded offset, the sizes add up (`bytes_before` is the size now plus, per place, the removed length less the replacement's), the file is not taken out as a whole, no place lost more than 256 bytes, and the kept bytes have the recorded fingerprint (a record from before `kept` existed, or an earlier redaction of a file redacted again, is checked without it). What was taken out is not in the folder, so verify cannot confirm that it was contact details, and says so: a file is "recorded as redacted by the researcher", and a pre-registered plan file whose only change since the freeze is a redaction whose records hold passes with "recorded as redacted by the researcher after registration (personal contact details, the record says)"; any other change still fails. A folder published before and redacted since still verifies against its `e2er.json` (with the redactions rolled back, `provenance.json` is the published one) until it is published again. `e2er redact <folder> --check --text <text>` rebuilds each redacted file's earlier version with the text and compares its hash value, so whoever knows the text can confirm that nothing else changed (a keyed fingerprint only on the computer that redacted the file). Text in a PDF (searched with `pdftotext`), a database or another binary file, or in a file `provenance.json` does not list, stops the redaction with nothing changed: redact the PDF's LaTeX source and let publish build the PDF again. Text in e2er's own records of the folder (`provenance.json`, `e2er.json`) cannot be redacted, and redact says so: take it out where it comes from (the run's workspace) and export again; the blind leak check says the same for these files and for the request and dossier built from them. A redaction changes the folder all or nothing: each file is written to a temporary file first and renamed into place, `provenance.json` last, and on any error (a full disk) every file is put back. Several `--text` are all or nothing too: if one is refused, the others are undone. `--check` with several `--text` checks each redaction with the text it took out. `--dry-run` says what would change. A later export of the run never rebuilds a redacted folder: a folder with amendments is kept like a published one, and the export makes a new numbered folder (make the redactions there again before publishing it).

**The dossier withholds the step fingerprints of a redacted file** (publications with the e2er release after 0.19.0 on). The run database records the SHA-256 of every file a step wrote; for a file redacted or anonymised later, such a fingerprint confirms a guess of the text taken out (put the guess where the replacement sits and hash). For every file with an amendment of kind `redacted`, `anonymised`, `abstract_rewritten` or `abstract_edited_by_researcher`, each fingerprint the dossier's workflow gives an earlier version of it (a step's output, `sha256_at_export`, a file the researcher supplied) becomes `"sha256": null` with `"withheld": "redacted after the step"` (or `anonymised`, `abstract rewritten`, `abstract edited`), and the same value elsewhere in the workflow, the events and the rounds goes too. Kept: the file as published, the pre-registration's frozen fingerprints (its lock file holds them, and anyone checks the deposited plan with them) and the fingerprints an amendment gives in plain (a folder published before). Every other file keeps its fingerprints, and a study without such an amendment keeps exactly its dossier and its address. `e2er verify` does not use the step fingerprints: it checks the folder against `provenance.json` and each amendment's own record. e2er.org shows "hash value withheld: redacted after the step". A dossier published before stays as it was published (its address is its hash): the school-fee demo (bhanneke/school-fee-abolition-enrolment-africa, versions 1 to 3) gives the earlier fingerprints of its two redacted files, `design/paper_plan.md` and `design/preregistration.md`, with the offsets and the length of the text taken out.

## Double-blind review

A journal with double-blind review must not learn who wrote a study, and neither may its reviewers. `e2er publish <folder> --blind --to https://e2er.org` publishes an anonymous version for them at `e2er.org/r/<code>`, an address made of 160 random bits that nobody can guess. e2er.org keeps the account that published it to itself and shows it to nobody: the page names no owner, handle, profile, ORCID iD or credit, and the version is in no list on e2er.org (studies, the home page, Discover, the search, the sitemap, people pages, the credit graph, the feeds and the API listings). Its pages carry `noindex`. The burst hold and withdrawal apply as to any version, and you see and manage it on your account page. `--owner` and `--project` are not needed.

**What happens on your computer first.** Publish works on a copy of the exported folder, next to it (`<folder>-anonymous-<first 8 characters of the code>`); the folder itself is not changed. On the copy it:

1. collects what identifies you: your e2er.org account's name, e-mail address and handles, and your profile's GitHub login, ORCID iD and affiliations (asked with `GET /api/v1/me`); the git author names and e-mail addresses of this computer and of the repository the study sits in; this computer's user name and host name; and whatever you add with `--blind-identifier "<text>"` (repeatable), `E2ER_BLIND_IDENTIFIERS` or `E2ER_AFFILIATION` (both separated by `;`), such as a co-author or your institute;
2. anonymises it with the machinery of `e2er redact`: the paper's author block becomes "Anonymous author(s)", affiliation, e-mail and `\thanks` commands keep their command with `[anonymised]` as their text, the acknowledgements become "Removed for double-blind review.", home-directory paths (`/Users/<name>`, `/home/<name>`, `C:\Users\<name>`) become `~`, and every identifier becomes `[anonymised]`. Each changed file gets an amendment in `provenance.json` of kind `anonymised`, with the rules applied and how many replacements of each kind it made, never the text taken out; verify refuses a record with an empty replacement, which would match anywhere. The fingerprint a file had before is not recorded either, and it is taken out of the dossier: with it, someone who guesses the text could put the guess back and compare. For the same reason the copy keeps no offsets and no sizes: an anonymisation records how many replacements of each kind it made, and the earlier amendments of `e2er redact` lose their offsets, the length of the text taken out and the file's fingerprint before (`e2er verify` counts the replacements in the file instead). A pre-registered plan file keeps its fingerprint before, which the lock file holds anyway. A folder with a symbolic link is refused: the link points outside the copy. Files `provenance.json` does not list (an earlier publish's `e2er.json`, `.e2er/`) are left out of the copy;
3. stamps the paper with the anonymous address and no author, and builds `paper/paper.pdf` again from the anonymised source (this needs tectonic);
4. runs the leak check: every text file, every PDF (its text from `pdftotext` and its bytes), every other file's bytes (zip archives and gzip files opened), the dossier and the request are searched for every identifier, in upper and lower case, URL-encoded, HTML- and JSON-escaped, with LaTeX accents, folded to ASCII ("Quarry" for "Quärry"), written in reverse ("Quärry, Imogen"), with initials ("I. Quärry"), split over lines or hyphenated, joined by `_`, `.`, `-` or nothing (`imogen_quarry.csv`, `ImogenQuarry`), with full-width letters, invisible characters (a zero-width space), HTML entities or %-escapes, and, for e-mail addresses, with "at" and "dot". File names are searched as well as contents; in a PDF also its metadata (`pdfinfo`), its compressed streams and its hex strings (UTF-16 titles); in a PNG its text chunks; any file's bytes also as UTF-16. Your surname alone and your first name with an initial ("Imogen Q.") may name you or someone else: publish lists them, and you confirm them with `--blind-ack-self-citations` as you confirm citations. Anything left is listed as file:line, and nothing is sent. A PDF that cannot be read (no `pdftotext`) and a compressed data file (Parquet, for instance) are listed too. e2er's own repositories (`github.com/bhanneke/E2ER-project` and the like), which every dossier names for the parts it pins, are not counted.

**Citing your own work.** Whether a citation gives you away cannot be judged mechanically. Names in the bibliography, in the references of a PDF, in citation keys and right before a year ("Quärry (2024)") are left as they are, and publish lists them, with the bibliography entries whose authors carry your surname and phrases such as "our previous work" or "we showed in". Read them (cite your own work in the third person, or leave it out), then publish again with `--blind-ack-self-citations`.

**What is refused.** `--github`, `--zenodo`, `--repo`, `--commit`, `--path`, `--data-url`, `--code-url`, `--paper-url`, `--paper public`, `--name`, `--orcid`, `--github-login`, `--coauthor`, `--derived-from`, `--no-stamp` and `--offline` each name you or a place that does, so publish refuses them with a plain message. Data and code may be stated public: they reach the reviewers in the package, and the anonymous version names no address for them. Data terms and the rules for what is left out of a package apply as usual.

**For the journal.** `e2er pack --blind <folder>` (the folder or its anonymised copy) writes the copy into `anonymous-<code>.e2er`, the file you upload as supplementary material. Its list of files names no author and no folder name, and it is checked for leaks once more. Reviewers run:

```bash
e2er verify anonymous-<code>.e2er --against https://e2er.org/r/<code>
e2er inspect anonymous-<code>.e2er
e2er reproduce anonymous-<code>.e2er
```

`--against` compares the file's content id with the anonymous version e2er.org published. The code in an anonymous package is a stranger's code: `e2er inspect` lists the commands `e2er reproduce` would run, and `e2er reproduce` lists them again and asks before it runs them, in a Docker container without network and without any folder of the reviewer's. Without Docker it runs nothing; `--no-sandbox` would run the code as the reviewer, and is not for an anonymous package.

**After the review.** Unblind the anonymous version on your account page on e2er.org (Anonymous versions, `https://e2er.org/account#blind`), signed in in the browser: you choose the handle and the study's name, and e2er.org publishes a new version with your name at `e2er.org/<handle>/<name>`, with the same files. A command-line token cannot unblind (a token that leaked, or a CI job's, must not be able to put your name on an anonymous version); `e2er publish <folder> --unblind <code>` says where to do it and sends nothing. To publish a named export of the study (with your name in the paper), publish it afterwards as a normal new version of that study, `e2er publish <named export> --owner <handle> --project <name> --to https://e2er.org`, checked as any version is. The anonymous version stays exactly as it was published, labelled "blinded", and its page links to the new version, which is labelled "unblinded" and links back. Nothing is ever unblinded without you.

**What stays possible.** The study's own content can still point to you: its topic, its data, a preprint of the same paper under your name, or the same study published on e2er.org with your name while it is under review (the paper's run id and the fingerprints of unchanged files would match). A pre-registered plan file that named you keeps its frozen fingerprint in `design/preregistration.lock.json` and in the dossier, because the pre-registration is checked against it; publish warns about such a file, since that fingerprint could confirm a guess of what was taken out. Take your name out of plan files before you freeze them.

## Writing a finished study's abstract again

`e2er abstract <folder>` runs e2er's abstract step on a study that was exported, or published, before the abstract had a step of its own (0.18.0). It lays the study out in a scratch folder (the final `paper/paper.tex`, the results, the reviews), runs the abstract writer once with the configured backend (`--backend`, `--model`), and then the abstract check: at most 160 words; no p-values, intervals, standard errors, Fisher-z or test statistics; at most three numbers, each a value of the study's results at the precision shown; a sentence that states a finding; a last sentence that is no negation and has no "rather than"; none of the constructions the phrase check refuses ("rather than", "X, not Y", the mirrored "changed A; changed nothing about B"). A failure sends the writer back once with the reasons; a second failure changes nothing in the folder. The calls' records go to a scratch database, never to the run's.

On a pass it puts the abstract into `paper/paper.tex` (in place of its abstract, or after the title where it had none), writes `paper/abstract.tex` (the study's `\title` stays in it when it was there), recompiles `paper/paper.pdf` with tectonic and shows the abstract in `report.html`. Each changed file gets an amendment in `provenance.json`: `{path, kind: "abstract_rewritten", sha256_before, sha256_after, bytes_before, model, backend, e2er_version, reason: "abstract rewritten by e2er's abstract step after the abstract fix; the paper's text and results are unchanged"}`, which the next publish puts in the dossier. The amendment of `paper/paper.tex` also records `abstract_before`: where the paper changed (`offset`, `length_after`), the text that stood there (published with the paper before) and the SHA-256 of the old abstract. `e2er verify` rebuilds the old paper from it: it must have the fingerprint `sha256_before` names, and everything outside the abstract (its environment, its `% src:` lines and keywords paragraph, the blank lines around it) must be byte for byte the same; an abstract amendment of any file other than these four fails. The command then runs the checks of `e2er verify` and puts every file back when they fail. A published folder still verifies against its `e2er.json` until it is published again (with these amendments rolled back, `provenance.json` is the published one); an amendment of `paper/paper.tex` written by e2er 0.18.0, without `abstract_before`, cannot be checked, so such a folder verifies against its `e2er.json` only once it is published again.

`e2er abstract <folder> --from-file <file> --reason "<why>"` puts the researcher's own abstract (a LaTeX abstract environment, or its text) in place of the writer's, for instance to correct one sentence of a written abstract. Nothing is sent to an AI. The abstract passes the same check, number check included, and each changed file gets an amendment of kind `abstract_edited_by_researcher` with the reason and `edited_by: "researcher"`.

## Demonstration studies

`e2er run --demonstration` (or the box in the dashboard's new-study form) marks a demonstration or test run when it starts; the choice is recorded in the study's manifest.json, and `e2er resume`, `e2er rerun`, export and publish keep it. `e2er publish --demonstration` (or `E2ER_PURPOSE=demonstration` in the study folder's `.env`) sets it at publishing: e2er.json and the dossier record `purpose: "demonstration"`, and the paper's first page carries the disclaimer; with `--template replication` the study is recorded as `kind: "replication"`, and the paper and the reproduction report carry the replication wording (src/core/demonstration.py).

The purpose recorded on the study when it started (the dashboard's "demonstration" box) counts as well; a study published again without a purpose loses the disclaimer in the report and on the paper.

## Checking a published study

`e2er verify <folder>` checks the folder against its own `provenance.json`, and `e2er.json` and `.e2er/link.json` against it. A folder published on a platform and then published again without `--to` (a deposit on Zenodo, or a send the platform refused) keeps the link to the platform's version, and the link records the description `e2er.json` now holds (`described_here`), so the folder still verifies and publishes again; a publish with `--to` writes the link anew. Whoever holds the folder can rewrite all three consistently, so this alone verifies the folder against itself, and verify says so. `e2er verify <folder> --against https://e2er.org/<owner>/<project>` also compares the folder's content id (the SHA-256 of `provenance.json`, which fixes every file) with the versions e2er.org published, reading them with a GET request; `--against https://e2er.org/r/<code>` compares it with an anonymous version for double-blind review, `--against https://e2er.org/d/<id>` compares the dossier, and `--against-file` a saved copy of either. After the checks, verify notes each sentence of `paper/paper.tex` and `paper/abstract.tex` that uses a construction the writing guidance rejects (the phrase check the draft writers' output contract applies during a run); the note changes neither the verdict nor the exit code.
